# 時計のログインは、本人が番号を見比べてからスマホが渡す

状態: 採用（2026-10-11、Wear OS 版。本人が「スマホから引き継ぐ」を選んだ）

## 背景

Wear OS 版（Galaxy Watch 7）でもスマホと同じことができるようにする。時計には YouTube のログインに使う WebView が無い（あっても文字の入力がつらい）ので、時計だけではログインできない。

ADR-0002 で、認証情報（cookie・SAPISID・visitorData・DATASYNC_ID）は端末の外へ出さないと決めた。ADR-0008 の中継にも載せない。時計に渡すのは、この決まりの唯一の例外になる。

## 決定

1. **経路は Wear OS の Data Layer（MessageClient）**。同じパッケージ名・同じ署名のアプリにしか届かない。中継（tailnet）は使わない
2. **頼むのは時計、送ると決めるのはスマホの本人**
   - 時計はその場限りの P-256 の鍵の組を作り（メモリだけ）、公開鍵を `/wave/login/request` でスマホへ送る
   - スマホは通知を出す。押すと確認の画面が開き、時計の公開鍵から作った6桁の番号を出す。時計にも同じ番号が出ている。本人が見比べて「送る」を押したときだけ送る。自動では送らない
   - スマホがログインしていなければ送らない
3. **中身はもう一段暗号化する**（Data Layer の暗号化に加えて）
   - スマホは使い捨ての P-256 の鍵で ECDH をとり、HKDF-SHA256（salt = 両方の公開鍵の SHA-256、info = `wave-watch-login-v1`）で AES-256-GCM の鍵を作る
   - 包むのは保存形式（`CredentialCodec`）の平文。`/wave/login/credentials` で頼んできた時計（ノード）にだけ送る
   - 時計は持っている秘密鍵で開き、`AuthManager.importFromPhone` で Keystore に保存する（スマホと同じ保存のしかた）。開けた後、鍵の組は捨てる。頼みは5分で切れる
4. **時計の側は、それぞれのログインとして扱う**。ログアウトは時計だけで行える。スマホでログアウトしても時計は続く（それぞれ YouTube の cookie を持つ）

## 結果

- 同じ cookie を2台が持つ。片方で YouTube からログアウトすると、両方が切れる（ADR-0004 の「期限切れ」の扱いになる）
- 番号を見比べずに「送る」を押すと、すり替えの鍵に送ってしまう可能性は残る（Data Layer は同じ署名のアプリにしか届かないので、すり替えには Google Play 開発者サービスの乗っ取りが要る）
- 6桁は約20ビットなので、Data Layer を乗っ取れる相手なら、同じ番号になる鍵を短い時間で探せる。番号は「別の時計に送っていないか」を本人が気づくためのもので、乗っ取られた Play 開発者サービスへの備えにはならない
