# ほかのアプリ向けの API は、中継の機械に置く「家の端末」が出す

状態: 採用（2026-10-19、本人の回答。「常駐を前提にしているのは中継のサーバーだけなので、そこに置く」「連携するときに、連携先のアカウントでログインを求める形にしたい」）

## 背景

home-dashboard（家の壁掛けの画面、`../home-dashboard`）などほかのアプリから、wave で再生中の曲を読み、操作し、曲やプレイリストを選んで鳴らしたい。鳴っている端末はスマホのことも PC のこともある。

- 家の再生の状態は中継（Connect v2）が持つが、中継は中身を読めない（ADR-0010、L-1）。中継に API を足しても、今の曲は分からない
- 各アプリに HTTP の口を開けると、その端末で鳴っているときしか使えず、スマホは裏で口を開け続けられない
- 自分のプレイリスト・高く評価した曲・おすすめは、YouTube のログインが要る

## 決定

1. **API は、中継と同じ機械（general-console）で常駐する別のプログラム `wave-api` が出す**（`api/`、`relay/deploy/compose.yaml` の別のコンテナ）
   - 中継のプロセスには入れない。中継は信用しない前提（L-1）を保ち、家の鍵は `wave-api` だけが持つ
   - `wave-api` は家の端末の1つとして、ほかの端末と同じく QR（の文字）と6桁で加わる。役割は player（遠隔操作・引き取りの頼みを出せるのは player だけのため）。ただし音は出さず、自分で再生を引き取らない（`adopt` を断る）。表示名は「wave API」、種類は `api`
   - 加入は家の端末（A）が QR を出し、`wave-api`（B）が `api pair '<QR の文字>'` で加わる。加わる時点ではログインを持たないので、加入のアカウントの照合（ADR-0008 のアカウントの HMAC）は、決まった印 `wave-accountless-v1` で作った HMAC で「ログインなしの相手」として通す（`Pairing.ACCOUNTLESS_ID`）。A はその相手を `peerAccountless` として受け、B は A のアカウントを確かめない
   - 印を受け入れるのは、A の本人が B の画面の6桁を A に入れて一致したときだけ（6桁の照合は前と同じく省かない）。アカウントの照合はもともと誤操作の防止で防御ではないので、守りは6桁の照合だけになる
   - 端末の画面は `api` の端末を「ここで再生」の行き先に出さない
2. **ログインは、加えた後に家の端末から渡す**（ADR-0011 の時計と同じく、ADR-0002 の「端末の外へ出さない」の例外）
   - 端末の連携の画面の `api` の端末に「ログインを渡す」を出す。本人が押して確かめたときだけ送る
   - 中身は命令（`login_grant`）で、宛先の `wave-api` の受け取りの鍵にだけ包む（ほかの端末には包まない）。送り手が署名する。中継は暗号文しか見ない
   - `wave-api` はログインを自分のファイル（ほかの人が読めない権限）に置く。端末の連携の画面から外すと（家から外す）、`wave-api` は次の起動で記録とログインを消す
   - ログインが無い間は、今の曲・キュー・端末の一覧・遠隔操作・端末の切り替えだけ使える（検索・プレイリスト・おすすめ・鳴らす・キューに足すは YouTube への問い合わせなので、ログインが要る。core の WaveSession はログインが無いと問い合わせない）。アカウントタグ（L-11）は鳴っている端末のカーソルのものを使い、ログインが届いたら自分で計算したものに替える
3. **API は HTTP（JSON）と、変化を流す SSE**
   - 待ち受けは 127.0.0.1（同じ機械の home-dashboard から）と、必要なら tailnet（`tailscale serve`）だけ。`Authorization: Bearer <トークン>` が要る（health を除く）
   - 口は `docs/wave-api.md` に書く。home-dashboard の `MusicProvider` の形（再生中・キュー・操作・プレイリスト・おすすめ・鳴らす・キューに足す）に合わせる
   - 「鳴らす」は、`wave-api` が曲・アルバム・プレイリストを読んでキューを作り、ほかの端末で鳴っている間に曲を選んだときと同じ手順（`playOn`）で、行き先の端末に引き取ってもらう。行き先を指定しなければ、鳴っている端末、無ければ最後に鳴った端末（どちらも中継につながっているとき）
4. **中継が受ける命令の大きさを 8KB から 16KB にする**（ログインの cookie が 4KB を超えることがあるため）

## Considered Options

### 中継のプロセスに API を入れる — 却下

中継が家の鍵を持つと、中継は中身を読めないという前提（L-1）が崩れる。同じ機械の別のプログラムなら、中継のコードと家の鍵を分けておける。

### 各アプリに HTTP の口を開ける — 却下

その端末で鳴っているときしか使えない。スマホは裏で口を開け続けられない。

### `wave-api` がログインを持たない — 却下（本人の回答）

自分のプレイリスト・高く評価した曲・おすすめが見えない。

### `wave-api` の上で WebView のログインを開く — 却下

サーバーには WebView が無い。家の端末から渡せば、ログインの手順を増やさずに済む。

## Consequences

- ログインなしの印で加わる相手は、アカウントの照合を通らない。別のアカウントでログインした家の端末の QR を読んでも、加入の段階では気づけない。ログインを渡すまでは、家の最後の再生を書いた端末のアカウントタグを借りるので、家に別のアカウントの端末があればその再生も読み・操作できる（ログインを渡した後は自分で計算したタグを使い、別のアカウントの再生には操作を送らない）。6桁を入れる本人の確かめが、加える相手を決める唯一の守りになる
- 加わった直後は、加わる前に書かれた状態（その時点の端末にだけ包まれている）を読めない。どこかの端末が次に書いたときから読める
- `wave-api` の機械に入れる人は、家の再生の状態と YouTube のログインを読める（その機械は家の端末の1つになる）
- `wave-api` は鳴らさないが player なので、家の再生を引き受けて書くことがある（「鳴らす」の間だけ。すぐ行き先の端末に引き取ってもらう）。引き取ってもらえなければ（行き先が切れた・断った）10秒で前の端末に戻る（ADR-0010 §5）
- 同じ cookie を家の端末と `wave-api` が持つ。片方で YouTube からログアウトすると両方が切れる
- トークンを知っていれば、家の音楽を操作でき、ログインで見えるもの（プレイリスト・高く評価した曲）を読める。トークンは `wave-api` の機械のファイルにだけ置く
