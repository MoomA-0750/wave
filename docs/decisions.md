## 2026-09-16 po_token を作らず、Premium のログインで直接取る

- Premium のアカウントなら、ストリームの URL から po_token を外しても曲が丸ごと取れることを実測した。Metrolist のように WebView で po_token を作る仕組み（タイムアウト・退避の分岐）を持ち込まない
- やめたこと: 匿名のクライアントを名乗る（1MB 超で拒否される）、SABR（自前の解析が要る、当面不要）
- 根拠: `5a219d9`、[ADR-0001](adr/0001-stream-acquisition.md)

## 2026-09-17 ログインは WebView、情報は端末の中だけに暗号化

- WebView で Google にサインインし、cookie を Keystore の鍵で暗号化して保存する。JS の口を公開しない、ログイン用の WebView のデータは起動のたびに消す
- debug ビルドでは WebView のリモートデバッグを止められないことを受け入れ、ログイン中はデバッガをつながない運用にした
- 根拠: `1c78d86`、`1d0e2a8`、[ADR-0002](adr/0002-webview-login-and-threat-model.md)

## 2026-09-17 認証の関所を HTTP の下の層に置く

- innertubex は、渡した HTTP クライアントを作り直す経路を持つため、プラグインで検査すると素通りする。エンジンを包む層で、決まった宛先以外へ認証のヘッダを出さないようにした
- やめたこと: Ktor のプラグインで検査する、innertubex を信用して検査しない
- 根拠: `44f0a87`、[ADR-0003](adr/0003-auth-header-guard.md)

- 根拠: `24d5b53`、[ADR-0004](adr/0004-session-expiry.md)

## 2026-10-14 曲ごとのログインの要求は、その曲だけの失敗にする

- 曲の再生の情報（/player）が `LOGIN_REQUIRED` を返したら、「その曲はログインの確認が要る」という失敗にして飛ばす。これまでは、ログインが切れた疑い（Suspect）にして、画面に「ログインを確かめています」を出していた。年齢確認の曲を流すたびにこれが出ていた
- 本当にログインが外れていた場合に気づけるよう、状態は変えずにアカウントのメニューで確かめる。ログアウトを示したときだけ失効にする。確かめの間隔の制限（同じ世代で1本・前回から一定時間）は今までと同じ
- `LOGIN_REQUIRED` の理由の文（「年齢を確認してください」「bot でないことを確認」など）で分けることは、やめた。文は言語ごとに変わり、YouTube の都合でも変わるため
- Premium の確認に使う固定の曲が `LOGIN_REQUIRED` を返したときは、今までどおり疑いにする（年齢確認の無い曲なので、ログインが外れた印になる）
- Windows・Mac・iPhone も同じ失敗の種類と文言にそろえた（これまでは「ログインが必要です」と出していた）

## 2026-10-14 連携の古い方式（v1）を消した

- v2（ADR-0010）が Android・時計（スマホ経由）・Windows・Mac・iPhone のすべてで動き、2026-10-13 に Pixel 3 と Windows の間でライブラリの同期まで確かめたので、SPEC の「予定」どおり v1 を消した。本人の回答は「進めてよい」。Windows・Mac・iPhone には初めから v1 が無かった（確かめた）
- 消したもの: Android の ConnectManager・PairingController・PairStore・RelayClient と v1 の画面（ペアの一覧・引き取り・解除・ペアリング）、v1 の debug の命令（`pair_*`・`take_over`）、`local.properties` の `wave.relayUrl`・`wave.relayHost`、`handoff-protocol` の Envelope・HandoffFlow・RelayMessages と封筒を封じる・開く処理、中継の RelayServer・Registry と v1 で起動する道
- 残したもの: 身元の署名鍵 DeviceIdentity（v2 も同じ鍵。消すと家の端末としての身元が変わる）、暗号の部品（WaveCrypto・Hpke・Pairing。Pairing は v2 の加入が拡張付きで使う）、端末 ID を出す `EnvelopeSealer.deviceId`（v2 の鎖・中継・Windows・Mac と同じ値。名前は付け替えずに残した）、`HandoffSnapshot`（v2 の家の状態の中身と、スマホと時計の間の再生の移動が使う。Windows・Mac も同じ形）、HandoffHost（時計との間の再生の移動が使う）
- 端末に残る v1 のファイル: `pairs.bin` と、それを包む Keystore の `wave-pairs-v1` は、起動時に消すことにした。中身は v1 のペアごとの封筒の鍵だけで、v2 は読まず、身元の鍵とも別なので、残す理由が無い。debug で書いた `pair-offer.txt`・`pair-code.txt` も消す。`connect-pubkey.txt` は v2 の家を作り直すときに `connect_info` で書き出す身元の公開鍵なので、`connect_info` ごと残した
- 中継は `WAVE_RELAY_PROTOCOL=v2` を必須にした。環境変数を外して v2 を既定にする案もあったが、v1 と v2 のコンテナが同じ配布物を見ているので、配布物を作り直した後に v1 のコンテナ（v2 の指定が無い）が起き直すと、v1 の登録ファイルを家のファイルとして読みにいく。指定が無ければはっきり止まるほうを選んだ
- v1 の中継のコンテナ（`dev/relay-deploy`、127.0.0.1:8790）は動いたまま。共有の資源なので、止めるのは本人の了承を待つ（SPEC の未決事項）。2026-10-19 の時点でコンテナは止まっていたので、手元の `dev/relay-deploy` はゴミ箱へ移した（tailscale serve の v1 の中継は外していない）
- ADR-0009 を「置き換え済み」、ADR-0008 を「一部置き換え済み」（身元・ペアリング・中継への署名の認証は v2 で生きている）にした

## 2026-10-14 歌詞から曲を探す

- 「予定」にあった歌詞から曲を探す機能を、検索の絞り込みの「歌詞」として作った（夜間に仮決定、本人の確認待ち）
- 予定では外部のサービスのキーが要るとしていたが、キーの要るサービスは使わないことにした。YouTube Music の絞り込まない検索に歌詞の一節を入れると、その曲が上位に出る（夜に駆ける・うっせぇわ・打上花火で、歌詞の行まで合うことを確かめた）。上位の6曲の歌詞を、再生画面と同じところ（LRCLIB、無ければ YouTube Music）から取り、打った言葉を含む曲を前に出す
- 曲に絞った検索は使わない。歌詞の一節では外れることが多かった（カーテンコール・Hello が出なかった）
- LRCLIB の検索（`/api/search`）は歌詞の本文を探さない（日本語の一節で0件）ので、使わない
- 照らし合わせは、大文字・小文字、全角・半角、カタカナ・ひらがな、空白と記号の違いを無視する。漢字とかなの違いは吸収しない。2行にまたがる一節も見つける。言葉が少し違うときは、2文字の組の7割が1行に入っていれば「大体合っている」とする
- 残る弱点: 一番上に出たのが投稿者の歌詞動画だけのとき（Adele の Hello など）は、題名が曲名と違うので歌詞が取れず、引用が付かない（検索の順のまま出す）

## 2026-10-16 曲送りの待ちと、再生の途中で止まる件

  - そこで端末の中に 127.0.0.1 でだけ待つ HTTP の受け口（LocalMediaServer）を立て、曲ごとに推測できない名前の下で、一覧と区切りのバイトを返す。署名付き URL は再生の部品に渡さないまま
- キャッシュ: 曲ごとに頭から途切れずに取れた分だけを残す形にした（区切りの穴を管理しないで済む。聴いた曲は聴いたところまで、次の曲は頭が残る）。形式（itag・長さ・目次の場所）も残し、頭が残っていれば /player を待たずに鳴らす。続きが要ったとき・再生履歴を送るときに URL を調べ、同じ形式（itag・長さ）でなければ使わない
  - 上限 300MB・ログアウトで全部消す（仮）。Mac・iPhone は Caches の wave-audio に置く（iPhone は OS が容量に困ると消すことがある）
  - Android は Media3 の SimpleCache・CacheDataSource を使う（鍵は videoId だけ。曲だけを通し、ライブと RSS は通さない）。次の曲の頭は CacheWriter で取る
  - Pixel で測るときの注意: ほかの端末を映していると、メディアボタンはその端末への遠隔操作になり、連携を往復する時間（0.6〜0.8 秒）を測ってしまう

## 2026-10-19 wave API へのログインの渡し方（Android・Windows・Mac・iPhone）

## 2026-10-22 Mac で右の欄を開いたまま検索すると落ちていたのを直す

- 症状: 右の欄（再生中・キュー）を開いた状態で、上の検索欄に打って Return を押すと、結果が届いたところで固まって落ちる。落ちた記録は AppKit の制約の更新の中止（`SplitViewChildController.hostingView(_:didUpdateMinSize:maxSize:)` から `setNeedsUpdateConstraints` が繰り返される）。右の欄を閉じていれば落ちない。ほかのページへ移っても落ちない

- 直し方: detail の根元に `.frame(minWidth: 0, maxWidth: .infinity, minHeight: 0, maxHeight: .infinity)` を付け、中身の最小の大きさを分け目へ伝えない。`maxWidth`・`maxHeight` だけの frame では中身の最小がそのまま外へ出るので直らなかった（試した）。区切りボタンの `.fixedSize()` を外す・読み込み中の輪を外す、も直らなかった

## 2026-10-27 Linux 版を Rust + GTK4/libadwaita で作り始める

- 本人の頼み: Linux 版を作る。GNOME を主に使うので画面は GTK。言葉は速さと効率で選び、各 OS で書き直している core を共通化できるならしたい
- 候補は Kotlin + java-gi（Android の core をすぐ使える）、Rust + gtk-rs、Python + PyGObject。本人の「速さと効率」に合わせて Rust にした
- Android の core はそのままでは共通化できない。innertubex が JVM（Android とデスクトップの JVM）でしか動かず、Kotlin/Native でも Swift・C# からも呼べないため
- Rust の core（linux/wave-core）は GTK に頼らず、外へ出す型を単純にして、後で UniFFI で Kotlin・Swift・C# から呼べる形にしておく。ほかの OS をこの core に寄せるかは Linux 版が動いてから、壊れやすい所（再生の URL の取り方など）から1つずつ決める（一度に置き換えると全 OS の確かめ直しが要るため）
- core の手本は、外の部品に頼らず自前で書いている Windows の Wave.Core（C#）にする
- 見た目の確かめは、mutter の headless（見えない仮の画面）の中で開き、アプリ自身に窓を PNG に書き出させる（linux/scripts/shot.sh）。作業中の画面に窓を出さない
- core の最初の分として、InnerTube の呼び出し（cookie・SAPISIDHASH・PREF・訪問者 ID・ログインの世代）、認証の情報（Debug に値を出さない）、曲の検索とホームの読み取りを Windows の Wave.Core から移した。読み取りの確かめは Android の core と同じ手本の応答（core/src/desktopTest/resources/fixtures）を使い、Windows のテストと同じことを確かめる
- HTTP は reqwest（rustls）。cookie はこちらで付け、転送（リダイレクト）は追わない（Windows と同じ）
- ログインは WebKitGTK（webkit6）で Windows と同じ流れにした。開いてよいホストを同じ一覧に絞り、music.youtube.com に着いたら cookie と yt.config_ の VISITOR_DATA・DATASYNC_ID を読む。ブラウザの記録は使い捨ての通信のまとまり（NetworkSession::new_ephemeral）にしてディスクに残さない。開発者ツールは切る
- ログインの情報は GNOME のキーリング（Secret Service）に oo7 で置き、ファイルには書かない
- core の通信は tokio の上で動かし、GTK の主スレッドからは結果を待つだけにする（linux/wave-gtk/src/runtime.rs）
- 再生の URL は Windows と同じく faraday の表とプレイヤーの JS で解く。JS の動作環境は QuickJS（rquickjs）。ネットワーク・ファイルに触れる手段は渡さない。プレイヤーは非 strict の JS（先頭の `var window=this;`）なので、rquickjs の既定の strict を切って読み込む（strict のままだと「window is undefined」で止まった）
- googlevideo は範囲を付けない取り方（丸ごと・bytes=0-）を 403 で拒む。playbin に URL を渡さず、core の RangeReader が 512KB ずつ範囲で取ったものを appsrc で流し込む（シークはその位置から取り直す。Windows の RangeStream と同じ考え）
- ログインしていないと、先頭の 1MB ほどの先が 403 になった（po_token が無い WEB の再生の振る舞いと見ている）。本人がログインした状態では 403 は出ず、検索から約 3.8 秒で鳴り始め、実時間で進んだ（音を出さない fakesink sync=true で確かめた）
- appsrc をどこからでも読める流れにすると、qtdemux は求めた長さ（例: 24 バイト目から 735 バイト）ちょうどを待ち、多く返すと「ファイルが壊れている」で止まった。512KB ずつ取った塊をとっておき、求められた長さだけを切り出して渡す
- 画面の並びは Mac・Windows と同じにし、部品は libadwaita（HeaderBar・NavigationView・ActionRow・StatusPage）。左・中央・右は角を丸めた欄（view の色）にする
- ジャケットは gtk::Picture だけだと画像の縦横の比に合わせて枠が伸び、横長の画像で正方形にならなかった。大きさの決まった枠の上に画像を重ねて切り抜く（gtk::Overlay と clip_overlay）
- ホームの横に流れる棚は、ScrolledWindow が中身の高さを測らず2行目の補足が切れたので、propagate_natural_height を付ける
- 下の帯の再生のボタンは、左右を SizeGroup で同じ幅にして窓の中央に置く。中央（シークバー）と左右の合計が窓に収まらないと中央からずれる（1280px の窓で 12px ずれた）ので、曲名を 22 文字・シークバーを 420px にした
- 見えない画面では押せないので、確かめるときだけ WAVE_DEMO_QUERY で「その語で検索して1曲目から流す」を指示できる
- GNOME のメディアの操作・メディアキーは MPRIS（org.mpris.MediaPlayer2.wave）で受ける。部品を足さず gio の D-Bus で直に出す。再生の状態は GStreamer から遅れて届くので、変化の知らせに加えて 0.5 秒ごとにも見て、変わったときだけ PropertiesChanged を出す。trackid は videoId の - を _ に替える（D-Bus のパスに - は使えない）
- ログアウトして入り直すと、MPRIS の口が古い再生を指したまま残り、メディアキーが止めたキューを操作し続ける。口は1つだけ持ち、入れ替えるときに D-Bus から外す（unregister_object と bus_unown_name）
- 歌詞は Windows の LyricsService と同じ順と覚え方で core に移した（YouTube Music の時刻付きは ANDROID_MUSIC として匿名で、LRCLIB は cookie を持たないクライアントで）。画面は Windows と同じく中央のページ
- GTK の CSS で var(--accent-color) を使うと、その規則が効かなかった（歌詞の大きさ・強調が出なかった）。@accent_color・@view_bg_color の書き方にする
- LRCLIB は Cloudflare の向こうで、一時的に 503 を返すことがあった（同じ問い合わせが少し後には 404）。失敗として扱い、結果を覚えない作りのままでよい
- 評価のボタンは emblem-favorite-symbolic だと色付きのハートで出て、付けたか見分けられなかった。GNOME の標準の starred-symbolic・non-starred-symbolic（色が変わる星）にする
- Claude の欄は Windows の AiChat と同じ作り（中継 ai-bridge、ai/agent.json を core に埋め込む、道具は手元で行う、知らない video_id は断る）。中継から届く1行ごとの出来事は tokio の上で読み、チャネルで主スレッドへ渡す。トークンは Debug に出さない
- 右の欄の中身を切り替える Stack は、既定ではいちばん広い中身に幅を合わせ、さらに中の入力の欄の hexpand が欄全体に伝わって、右の欄が 500px 以上に広がった。Stack を hhomogeneous=false にし、Clamp で 340px に抑え、欄の hexpand を明示的に切る
- 確かめは、手元に立てた試しの中継（答えを少しずつ返し、search_songs と show_songs を呼ぶ）で行った。本物の中継（本人の PC の ai-bridge）では未確認
- MV は Windows の MusicVideoPlayer と同じく、音とは別の音を消した映像を音の位置に合わせ続ける（ずれが 400ms を超えたら映像を飛ばす）。映像は gtk4paintablesink（Fedora の GStreamer に入っている）で描き、その絵を gtk::Picture に渡す。範囲で取って appsrc に流し込む仕組みは音と共有する。解読の準備（プレイヤーの JS）も音と映像で1つを共有する

## 2026-11-08 Linux の aarch64 版は aarch64 の機械で組む

## 2026-11-08 Linux はブラウザのログインを読んで使える

- 本人の頼み: 「ログイン情報をブラウザから持ってくる、あるいはそのログインをブラウザでやるようにして欲しい」
- ふだんのブラウザで済ませたログインを、アプリへ戻す口は無い（拡張を入れない限り）。そこで、ブラウザの cookie の DB を読む形にし、見つからなければ music.youtube.com をふだんのブラウザで開いて、ログインしてから押し直してもらう。二つの頼みを一つの流れでかなえる
- 読むのは押したときだけで、ログインが残っているプロファイルを並べて本人に選ばせる（黙って読まない）。値を読むのは選んだ1つだけ。DB は $XDG_RUNTIME_DIR の自分だけが読める置き場へ写して開き、すぐ消す（ブラウザが開いたままでも読める）
- Firefox の系統は既定の入れ物（originAttributes が空）だけ。コンテナーやプライベートの窓のログインは混ぜない
- Chromium の系統は v10（決まった鍵）・v11（キーリングの鍵）を解き、DB の版 24 からの値の頭のホストの SHA-256 を確かめる（鍵の取り違えを見分ける）
- 保存の前に music.youtube.com を1度開いて LOGGED_IN を確かめ、VISITOR_DATA・DATASYNC_ID もそこで取る（WebKit の窓のログインと同じものを持つ）
- ブラウザとログインを分け合うので、ブラウザでログアウトすると wave のログインも切れる。そのときは押し直せばよい
- Windows は Chrome・Edge の cookie が App-Bound の暗号で外から読めず、Android・iPhone はほかのアプリの cookie を読めないので、Linux だけにした

## 2026-11-09 Mac・iPhone のショートカットから、どの曲・ライブでも鳴らせるようにする

- 本人の頼み: 「Mac/iOSで、特定の曲やライブストリームなどをショートカットアプリから再生できるようにしたいです」
- 「選んだものを再生」の候補は、アプリが items.json に書いたもの（ライブラリ・再生履歴・この端末で鳴らしたもの）だけで、聞いたことの無い曲は選べなかった。一覧で文字を打ったとき、アプリの中で動いていれば YouTube Music も検索して「検索結果」の見出しで後ろに並べる。ウィジェットの拡張は YouTube に触れない作りなので、拡張が一覧を出したときは手元の候補だけのまま（検索の口は WidgetBridge に、アプリの起動時に入れる）
- 選んだものは今までどおり中身ごと ID（token）に入るので、検索結果から選んだものも候補から外れて鳴らせる
- 一覧に頼らず決まったものを鳴らす口として「リンクで再生」を足した。共有のメニューでコピーしたリンクをそのまま貼れ、ショートカットの中で文字を組み立てても渡せる。曲かライブかはリンクから分からないので、next の先頭の曲で題・アーティストを取ってから鳴らす。配信中のライブには next の行に liveBadge が付く（2026-11-09 にログインあり・なしの両方で Lofi Girl の配信 4t4AQ15yj1M で確かめた）ので、MusicParsers.playlistPanelSong でライブの印にする。配信を終えた動画（jfKfPfyJRdk など）は長さの欄に経過時間（33,778:11:52 のような値）が入り、バッジは付かない。長さが無いものをライブと見なす案は、この長さが読めずに終わった配信をライブと取り違えたのでやめた。外れても、鳴らすときに再生の側がライブと見分け直す
- ID だけのときの見分け方は Android の PlayLink.parse にそろえた（MPREb_ → アルバム、11字 → 動画、PL・OLAK5uy_・RD → プレイリストの順。v= と list= の両方があれば動画、スキームが無くても読む）
- プレイリストは鳴らす前に最初のページを読んで、読めなければ誤りを返す（鳴らす手順は「選んだものを再生」と同じ）。ミックス（RD…）はプレイリストのページとして読めないものがあるので、そのときは next の曲を流す
- 同じものが鳴っている最中に頼まれたら、「選んだものを再生」は一時停止にするが、「リンクで再生」は何もしない（「鳴らして」という頼みで止まるのは意外なため）
- リンクを読む部分は WaveCore の YouTubeLink に置き、swift test で確かめる。Siri の言い方にパラメーターの文字（リンク）は入れられないので、「wave でリンクを再生」だけ足した
