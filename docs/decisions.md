# 判断の記録

なぜそうしたか、試してやめたことを、日付付きで古い順に追記する。書き換えはせず、考えが変わったら新しい日付で書き足す。
詳しい理由のあるものは [ADR](adr/) に書いてあり、ここでは要点と根拠だけを残す。2026-10-14 より前の分は、commit の履歴・ADR・本人のメモから後でまとめたもの。推測は「（推測）」と書く。

## 2026-09-16 po_token を作らず、Premium のログインで直接取る

- Premium のアカウントなら、ストリームの URL から po_token を外しても曲が丸ごと取れることを実測した。Metrolist のように WebView で po_token を作る仕組み（タイムアウト・退避の分岐）を持ち込まない
- やめたこと: 匿名のクライアントを名乗る（1MB 超で拒否される）、SABR（自前の解析が要る、当面不要）
- 根拠: `5a219d9`、[ADR-0001](adr/0001-stream-acquisition.md)

## 2026-09-16 通信は innertubex、共有コアは Kotlin Multiplatform、UI は OS ごと

- InnerTube の通信は innertubex を使い、自前で作らない。innertubex が GPL-3.0 なので、wave も GPL-3.0 にした
- UI は各 OS の部品で個別に書き、共有するのはコアだけにする。Linux のデスクトップは対象外
- 根拠: `f24aefc`、本人のメモ（D-001〜D-005）

## 2026-09-16 試験のための cookie の受け渡しをやめた

- Phase 0 で cookie を PC 側へ渡して試そうとしたところ、Claude Code の安全の判定に止められた。ログインの情報は端末の上だけに置き、PC には一切降ろさない方針にした。予定していた試験（M4）は後の実装で自然に確かめることにした
- 根拠: 本人のメモ（Phase 0 の記録）

## 2026-09-17 ログインは WebView、情報は端末の中だけに暗号化

- WebView で Google にサインインし、cookie を Keystore の鍵で暗号化して保存する。JS の口を公開しない、ログイン用の WebView のデータは起動のたびに消す
- debug ビルドでは WebView のリモートデバッグを止められないことを受け入れ、ログイン中はデバッガをつながない運用にした
- 根拠: `1c78d86`、`1d0e2a8`、[ADR-0002](adr/0002-webview-login-and-threat-model.md)

## 2026-09-17 認証の関所を HTTP の下の層に置く

- innertubex は、渡した HTTP クライアントを作り直す経路を持つため、プラグインで検査すると素通りする。エンジンを包む層で、決まった宛先以外へ認証のヘッダを出さないようにした
- やめたこと: Ktor のプラグインで検査する、innertubex を信用して検査しない
- 根拠: `44f0a87`、[ADR-0003](adr/0003-auth-header-guard.md)

## 2026-09-17 ログインが切れたかは、確かめてから決める

- 401 はすぐ失効。403 や `LOGIN_REQUIRED` は bot の確認やレート制限でも返るので「疑い」にとどめ、アカウントのメニューで確かめてから決める（Fable の指摘を受けて）
- 根拠: `24d5b53`、[ADR-0004](adr/0004-session-expiry.md)

## 2026-09-17 faraday を有効にし、第三者の JS が動きうることを受け入れる

- YouTube のプレイヤーの変化に強くするため、innertubex の faraday を有効にした。最初は「faraday の中身が JS として実行されることは無い」と書いたが誤りで、表に無いプレイヤーでは前処理済みの JS を取って QuickJS で動かす。これを受け入れて ADR を訂正した
- 根拠: `0b64bf2`、[ADR-0005](adr/0005-faraday.md)

## 2026-09-17 UI の作り込みを後回しにして、機能を先に

- 実機での通しの確認を後回しにして、選曲・再生・キューまで前倒しで進めた。その後も「普段使いの機能 → 端末の連携 → Claude 連携 → ほかの OS」の順で、UI の作り込みは後にした
- 根拠: 本人のメモ（D-014・D-017）

## 2026-09-17 再生履歴は music.youtube.com に向けて送る

- 再生履歴の送り先を music.youtube.com に書き換えて送れば足りることを実機で確かめた。cookie を送る宛先を増やさない
- 他のアプリのメディアボタンで一時停止中のキューが再生され、履歴に載ることは受け入れた（本人の決定）。プロセスが無い状態からの復元は自分の画面がつながったときだけにして塞いだ
- 根拠: `6fceee1`、`db7196c`、`3ce7305`、[ADR-0006](adr/0006-playback-history.md)

## 2026-09-17 書き込み先のアカウントを確かめる

- 重いレビュー（Codex）で、書き込みの主体を確かめていないこと、アカウントの切り替えが1つの手続きになっていないことを指摘された。DATASYNC_ID で確かめ、要求ごとにログインの世代で照らすようにした
- 根拠: `01241e1`、`36799e9`、`06fb6fb`、[ADR-0007](adr/0007-account-identity-and-generation.md)

## 2026-09-17 端末の連携 v1: 自宅の中継を通し、中継を信用しない

- 外出先からも受け渡せるよう、自宅の中継を通す。中継は乗っ取られうる前提で、ペアごとの鍵で守る
- 暗号は最初 Tink を考えたが、Android 標準の部品と HKDF（テストベクタ付き）にした。端末の実測で X25519 が使えず P-256 にした
- v1 は「手元の端末が再生中の端末から引き取る」だけにした
- 根拠: `3316ad5`〜`16c652a`、[ADR-0008](adr/0008-connect-trust-model.md)、[ADR-0009](adr/0009-handoff-procedure.md)

## 2026-09-18 端末の連携 v2: 中継が家の状態を持つ

- v1 は、引き取られる側がその瞬間に中継につながっている必要があり、引き取る前に相手が何を鳴らしているか分からなかった。本人の希望で、Spotify Connect のように中継が家の再生状態を持つ形（v2）にした。中継を信用しない前提は保ち、端末ごとの鍵で暗号化する
- 2台が同時に鳴ったときの止まる規則は、端末の時計を使わず、相手の再生を見てから始めた方を後とする
- v1 は並べて残している（消すのは2台で確かめた後の予定）
- 根拠: `e70ea02`〜`abdfb33`、[ADR-0010](adr/0010-connect-v2-state-server.md)

## 2026-10-06 連携に遠隔操作と「ここで鳴らす」を足す
