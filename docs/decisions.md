## 2026-09-16 po_token を作らず、Premium のログインで直接取る

- Premium のアカウントなら、ストリームの URL から po_token を外しても曲が丸ごと取れることを実測した。Metrolist のように WebView で po_token を作る仕組み（タイムアウト・退避の分岐）を持ち込まない
- やめたこと: 匿名のクライアントを名乗る（1MB 超で拒否される）、SABR（自前の解析が要る、当面不要）
- 根拠: `5a219d9`、[ADR-0001](adr/0001-stream-acquisition.md)

## 2026-09-16 通信は innertubex、共有コアは Kotlin Multiplatform、UI は OS ごと

- 根拠: `f24aefc`、本人のメモ（D-001〜D-005）

- 根拠: 本人のメモ（Phase 0 の記録）

## 2026-09-17 ログインは WebView、情報は端末の中だけに暗号化

- WebView で Google にサインインし、cookie を Keystore の鍵で暗号化して保存する。JS の口を公開しない、ログイン用の WebView のデータは起動のたびに消す
- debug ビルドでは WebView のリモートデバッグを止められないことを受け入れ、ログイン中はデバッガをつながない運用にした
- 根拠: `1c78d86`、`1d0e2a8`、[ADR-0002](adr/0002-webview-login-and-threat-model.md)

## 2026-09-17 認証の関所を HTTP の下の層に置く

- innertubex は、渡した HTTP クライアントを作り直す経路を持つため、プラグインで検査すると素通りする。エンジンを包む層で、決まった宛先以外へ認証のヘッダを出さないようにした
- やめたこと: Ktor のプラグインで検査する、innertubex を信用して検査しない
- 根拠: `44f0a87`、[ADR-0003](adr/0003-auth-header-guard.md)

## 2026-09-17 ログインが切れたかは、確かめてから決める

- 根拠: `24d5b53`、[ADR-0004](adr/0004-session-expiry.md)

## 2026-10-14 曲ごとのログインの要求は、その曲だけの失敗にする

- 曲の再生の情報（/player）が `LOGIN_REQUIRED` を返したら、「その曲はログインの確認が要る」という失敗にして飛ばす。これまでは、ログインが切れた疑い（Suspect）にして、画面に「ログインを確かめています」を出していた。年齢確認の曲を流すたびにこれが出ていた
- 本当にログインが外れていた場合に気づけるよう、状態は変えずにアカウントのメニューで確かめる。ログアウトを示したときだけ失効にする。確かめの間隔の制限（同じ世代で1本・前回から一定時間）は今までと同じ
- `LOGIN_REQUIRED` の理由の文（「年齢を確認してください」「bot でないことを確認」など）で分けることは、やめた。文は言語ごとに変わり、YouTube の都合でも変わるため
- Premium の確認に使う固定の曲が `LOGIN_REQUIRED` を返したときは、今までどおり疑いにする（年齢確認の無い曲なので、ログインが外れた印になる）
- Windows・Mac・iPhone も同じ失敗の種類と文言にそろえた（これまでは「ログインが必要です」と出していた）

## 2026-10-14 連携の古い方式（v1）を消した

- v2（ADR-0010）が Android・時計（スマホ経由）・Windows・Mac・iPhone のすべてで動き、2026-10-13 に Pixel 3 と Windows の間でライブラリの同期まで確かめたので、SPEC の「予定」どおり v1 を消した。本人の回答は「進めてよい」。Windows・Mac・iPhone には初めから v1 が無かった（確かめた）
- 消したもの: Android の ConnectManager・PairingController・PairStore・RelayClient と v1 の画面（ペアの一覧・引き取り・解除・ペアリング）、v1 の debug の命令（`pair_*`・`take_over`）、`local.properties` の `wave.relayUrl`・`wave.relayHost`、`handoff-protocol` の Envelope・HandoffFlow・RelayMessages と封筒を封じる・開く処理、中継の RelayServer・Registry と v1 で起動する道
- 残したもの: 身元の署名鍵 DeviceIdentity（v2 も同じ鍵。消すと家の端末としての身元が変わる）、暗号の部品（WaveCrypto・Hpke・Pairing。Pairing は v2 の加入が拡張付きで使う）、端末 ID を出す `EnvelopeSealer.deviceId`（v2 の鎖・中継・Windows・Mac と同じ値。名前は付け替えずに残した）、`HandoffSnapshot`（v2 の家の状態の中身と、スマホと時計の間の再生の移動が使う。Windows・Mac も同じ形）、HandoffHost（時計との間の再生の移動が使う）
- 端末に残る v1 のファイル: `pairs.bin` と、それを包む Keystore の `wave-pairs-v1` は、起動時に消すことにした。中身は v1 のペアごとの封筒の鍵だけで、v2 は読まず、身元の鍵とも別なので、残す理由が無い。debug で書いた `pair-offer.txt`・`pair-code.txt` も消す。`connect-pubkey.txt` は v2 の家を作り直すときに `connect_info` で書き出す身元の公開鍵なので、`connect_info` ごと残した
- 中継は `WAVE_RELAY_PROTOCOL=v2` を必須にした。環境変数を外して v2 を既定にする案もあったが、v1 と v2 のコンテナが同じ配布物を見ているので、配布物を作り直した後に v1 のコンテナ（v2 の指定が無い）が起き直すと、v1 の登録ファイルを家のファイルとして読みにいく。指定が無ければはっきり止まるほうを選んだ
- v1 の中継のコンテナ（`dev/relay-deploy`、127.0.0.1:8790）は動いたまま。共有の資源なので、止めるのは本人の了承を待つ（SPEC の未決事項）
- ADR-0009 を「置き換え済み」、ADR-0008 を「一部置き換え済み」（身元・ペアリング・中継への署名の認証は v2 で生きている）にした

## 2026-10-14 歌詞から曲を探す

- 「予定」にあった歌詞から曲を探す機能を、検索の絞り込みの「歌詞」として作った（夜間に仮決定、本人の確認待ち）
- 予定では外部のサービスのキーが要るとしていたが、キーの要るサービスは使わないことにした。YouTube Music の絞り込まない検索に歌詞の一節を入れると、その曲が上位に出る（夜に駆ける・うっせぇわ・打上花火で、歌詞の行まで合うことを確かめた）。上位の6曲の歌詞を、再生画面と同じところ（LRCLIB、無ければ YouTube Music）から取り、打った言葉を含む曲を前に出す
- 曲に絞った検索は使わない。歌詞の一節では外れることが多かった（カーテンコール・Hello が出なかった）
- LRCLIB の検索（`/api/search`）は歌詞の本文を探さない（日本語の一節で0件）ので、使わない
- 照らし合わせは、大文字・小文字、全角・半角、カタカナ・ひらがな、空白と記号の違いを無視する。漢字とかなの違いは吸収しない。2行にまたがる一節も見つける。言葉が少し違うときは、2文字の組の7割が1行に入っていれば「大体合っている」とする
- 残る弱点: 一番上に出たのが投稿者の歌詞動画だけのとき（Adele の Hello など）は、題名が曲名と違うので歌詞が取れず、引用が付かない（検索の順のまま出す）

## 2026-10-16 曲送りの待ちと、再生の途中で止まる件

- 調べたこと: Mac・to-fu・Pixel 3 で曲送り・戻しを測り、記録を読んだ。押してから鳴るまで Pixel 0.2〜0.6 秒、Windows 0.4〜1.2 秒、Mac 1.5〜2 秒

  - 試してやめたこと: 一覧と区切りを独自の URL（wave-media://、AVAssetResourceLoader）で渡す形。AVPlayer は HLS の区切りを独自の URL では読まず（OS の記録に `-12881 custom url not redirect`）、鳴らなかった
  - そこで端末の中に 127.0.0.1 でだけ待つ HTTP の受け口（LocalMediaServer）を立て、曲ごとに推測できない名前の下で、一覧と区切りのバイトを返す。署名付き URL は再生の部品に渡さないまま
- キャッシュ: 曲ごとに頭から途切れずに取れた分だけを残す形にした（区切りの穴を管理しないで済む。聴いた曲は聴いたところまで、次の曲は頭が残る）。形式（itag・長さ・目次の場所）も残し、頭が残っていれば /player を待たずに鳴らす。続きが要ったとき・再生履歴を送るときに URL を調べ、同じ形式（itag・長さ）でなければ使わない
  - 上限 300MB・ログアウトで全部消す（仮）。Mac・iPhone は Caches の wave-audio に置く（iPhone は OS が容量に困ると消すことがある）
  - Android は Media3 の SimpleCache・CacheDataSource を使う（鍵は videoId だけ。曲だけを通し、ライブと RSS は通さない）。次の曲の頭は CacheWriter で取る
  - Pixel で測るときの注意: ほかの端末を映していると、メディアボタンはその端末への遠隔操作になり、連携を往復する時間（0.6〜0.8 秒）を測ってしまう


## 2026-10-16 iPhone の実機で分かったこと（音楽の小窓・中の受け口・遠隔の一時停止）

## 2026-10-16 スマホの音量のバー・下へ払って閉じる・横向きのジャケットの影

- 本人から「スマホ版の音量バーは本体の音量を調整するようにして欲しい」と頼まれた。これまでは、ほかの端末から下げられたアプリの中の音量を戻すときだけバーを出していた。手元で鳴らしている間は常にバーを出し、本体の音量を動かす。遠隔から本体の音量は変えない、という決まりはそのまま（ほかの端末から届く音量はアプリの中の音量）。バーには「本体の音量 × アプリの中の音量」を出す。触ったらアプリの中の音量を 100 に戻し、その分を本体へ移す。こうすると音の大きさが跳ねず、下げられたアプリの中の音量も戻せる
- iPhone は、アプリから本体の音量を変える公の方法が MPVolumeView のつまみしか無い。見えないものを画面の外に置き、そのつまみを動かす。真ん中に置くと、透明度 0.01 でもつまみの下にうっすら見えた。outputVolume は止めている間は変わらないことがあった。鳴らしている間は、命令で指定した値どおりに変わった
- 再生画面を下へ払って閉じる操作: iPhone はジャケットの横に払う操作が下へ払う操作を横取りし、ほかの場所ではスクロールと取られていた。ジャケットの払いは縦の動きも通すようにし、スクロールが一番上でさらに 70pt 引っ張られたら閉じるようにした。Android には払って閉じる操作が無かった。入れ子のスクロールで余った下向きの動きを画面のずれにし、離したときに 120dp を超えているか速く払っていれば閉じる
- 横向きの前後のジャケットのはみ出しは、枠のすぐ外で切ったことで、真ん中のジャケットの影がくっきり切れて見えていた。前後のジャケットは払っている間だけ出し、間を 64pt に広げ、切る位置を枠の外 40pt（縦は大きく）に離した

## 2026-10-16 映像の全画面で操作を重ねる・iPhone で戻ったら映像の小窓を閉じる
